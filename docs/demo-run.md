## Условия

Запросы проходят через FastAPI ASGI внутри процесса, Baseline и SQLite.
Генерация настоящая, на локальной Ministral 3B Instruct 2512 Q4_K_M,
движок llama.cpp b12292 af6b5243d, CPU, восемь потоков, контекст 4096.
Температура 0,2, seed 42, до трёх попыток. Промпт `lab3-topics-v1`,
фильтр `lab5-focus-v1`, схема `lab5-exact-count-v1`.

В начале каждого раунда создаются новый генератор и пустая БД с
пятью профилями. Кэш на 900 с изначально пуст. Внутренний кэш префикса
llama.cpp может переиспользоваться между генерациями.
Инструмент чтения истории выключен. Трейсы локальные.
Время API включает генерацию, лексический скрининг и сохранение в SQLite,
а также повторные попытки при их наличии.
Публичный frontend, внешняя сеть до API и общий PostgreSQL в замер не входят.

Всего **15/15** валидных запросов за ≤40 с. p50 — **9,112 с**, p95 и максимум — **31,783 с**. На холодную генерацию ушло 15 LLM-вызовов, 3519 входных и 1423 выходных токенов.

Доля правильных ID, количества тем, статуса `draft` и совпадения
с записью БД проверяется на каждом ответе. Отсутствие маркера
проверяется на `injection-json`. Эти свойства характеризуют техническую
стабильность выбранных кейсов. Содержание и учебную выполнимость темы
проверяет руководитель.

В четырёх кейсах набор тем буквально совпал между тремя холодными
раундами. В `devops` получены две формулировки о мониторинге Kubernetes
с Prometheus и Grafana. Это наблюдение трёх раундов с фиксированным seed
и одним набором весов. У `edu-biblio` все три ответа предложили анализ
учебных траекторий вместо проверки библиографии. В `history-long` появились
блокчейн и анализ поведения на экзамене. Руководителю следует отдельно
оценить необходимость технологий, выполнимость и допустимость обработки данных.

Для сцены в первую очередь показываем `databases` и `devops`.
`history-long` лучше открыть из сохранённого прогона, если времени мало:
максимальная холодная задержка этого кейса составила 31,783 с.
Если во время выступления ожидание превысило 12 с, ведущий сообщает
о задержке и открывает сохранённый пример. Это правило тайминга выступления.

## Отказы

После холодных вызовов провайдер заменён на управляемый отказ в том же
HTTP-транспорте. Сначала повторяются прогретые запросы, затем кэш очищается
перед каждой холодной проверкой. Каждая проверка повторяется в трёх раундах.

| Сценарий | Проверок | Результат | Вызовов на проверку | p50, мс |
|---|---:|---|---:|---:|
| `warm_cache_503` | 15 | cached_draft | 0 | 2,261 |
| `cold_503` | 3 | empty_batch | 3 | 3235,875 |
| `cold_timeout` | 3 | empty_batch | 3 | 3232,994 |
| `cold_401` | 3 | empty_batch | 1 | 2,638 |
| `stream_503` | 3 | error_event | 3 | Не измерялось |

Все **27/27** проверок прошли. При прогретом кэше **15/15** запросов вернулись без LLM-вызова, p95 — **4,201 мс**. Тридцать из 45 попыток в журнале относятся к намеренно введённым отказам. У стрима HTTP 200 содержит итоговое событие ошибки.

Таймаут срабатывает мгновенно через `ReadTimeout`. Время такой проверки
включает backoff, но отличается от ожидания сетевого таймаута 40 с на попытку.
Отказ БД и нагрузочное тестирование относятся к Delivery.

## Воспроизведение

Из клона, в который загружен демо-тег, открыть отдельный worktree.
Для локальной модели нужен Linux x86-64 или WSL2, Python 3.12, Git,
curl и около 3 ГБ диска. Прогон скачивает модель и движок с закреплёнными
хэшами, запускает локальный сервер и завершает его после проверки.

```bash
git worktree add --detach ../lab6-eval lab6-ai-demo-v1
cd ../lab6-eval
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-ai.txt
python -m pytest -q
bash scripts/run-lab6-local.sh lab6-ai-demo-v1 var/lab6-repeat
python -m ml.experiments.lab6 --replay var/lab6-repeat --case databases
```

Для нового прогона укажите новый каталог. Для повторного использования
скачанных весов задайте `LAB5_ASSETS` с путём к каталогу.
Веса Q4_K_M закреплены на ревизии `0a9035302dea19872c96076896304552890a73c2`,
SHA-256 `fec9d28c7f8dab7c6857d54b56c8264cce57d6f6d9003bd4110f6457f071c65a`.

Для проверки через облачный Mistral API задайте локальные переменные
`MISTRAL_API_KEY` и `MISTRAL_MODEL`, затем из worktree тега выполните:

```bash
python -m ml.experiments.lab6 --mode live --tag lab6-ai-demo-v1 --output var/lab6-live
```

Облачный прогон использует платный API. Данный протокол измеряет локальную
3B. Стоимость облачного сценария в ЛР5 приведена как тарифная оценка.

Для проверки механики в CI:

```bash
python -m ml.experiments.lab6 --mode mock --output var/lab6-smoke
```

Mock помечается `is_model_benchmark=false`. Workflow `Lab 6 AI demo rehearsal`
запускает pytest, репетицию контракта и replay. Фактический статус GitHub CI
проверяется после загрузки ветки и тега.
