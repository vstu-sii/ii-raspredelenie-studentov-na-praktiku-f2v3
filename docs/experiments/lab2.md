# Spike 1. Размер structured output и устойчивость массовой генерации

## Вопрос

**Нужно ли в первом LLM-вызове сразу получать `title + rationale + keywords`, или достаточно
компактного `titles[]`?**

## Рискованное допущение

Предполагалось, что небольшой Ministral 8B стабильно успеет сформировать длинный structured JSON
в установленный timeout даже при массовой генерации.

## Что проверили

В раннем варианте модель должна была вернуть для каждого кандидата:

```json
{
  "title": "...",
  "rationale": "...",
  "keywords": ["...", "..."]
}
```

На реальном прототипе наблюдались случаи, когда
`ministral-8b-2512` не успевала завершить structured response за 40 секунд.

После этого контракт первого вызова был сокращён до:

```json
{
  "teacher_id": 1,
  "titles": ["...", "..."]
}
```

Локальные проверки профиля, дублей и Quality Gate не требуют `rationale` от LLM и выполняются
после ответа.

## Измерение размера

На текущих JSON Schema:

| Артефакт | Размер |
|---|---:|
| rich schema (`title+rationale+keywords`) | 500 bytes |
| compact schema (`titles[]`) | 302 bytes |
| пример rich response на 7 кандидатов | 3157 bytes |
| пример compact response на 7 кандидатов | 1407 bytes |

Примерный compact/rich ratio ответа: **0.44**.

То есть представительный компактный ответ составляет около **44%** размера rich-варианта.

Важно: размер JSON сам по себе не доказывает пропорциональное уменьшение latency —
время ответа зависит и от нагрузки провайдера. Это только управляемый фактор, который мы можем сократить.

## Практический результат

После перехода на компактный контракт был выполнен массовый запуск `batch #25`,
в котором сохранено **112 тем**, и все они имели provenance Mistral AI без подмешивания локального банка.

## Вывод

**Исходное допущение сработало иначе.**

Structured Output нужен, но богатый объект в первом вызове не нужен.

Решение:

> первый AI-вызов возвращает только `teacher_id + titles[]`; всё, что можно вычислить локально,
> вычисляется локально.

Это уменьшает output budget и снижает риск timeout без потери контрольных механизмов.

# Spike 2. Достаточна ли lexical similarity

## Вопрос

**Сможет ли лексическое сравнение надёжно ловить смысловые дубли прошлых тем?**

## Рискованное допущение

Можно использовать один общий порог `45/70` даже когда embedding-модель недоступна и проверка
деградировала до lexical-only режима.

## Данные

Взяты три пары, которые человек считает близкими по смыслу:

### Пара 1

Прошлая тема:

> Многоагентная система глубинного изучения математических дисциплин с автогенерацией
> пермонализированных заданий

Новая тема:

> Разработка системы автоматической генерации и проверки учебных заданий с адаптацией сложности

### Пара 2

Прошлая тема:

> Многоагентная система фиксации и управления историей разработки учебных и научных работ

Новая тема:

> Разработка системы управления и анализа истории разработки научных проектов вуза
> с визуализацией зависимостей

### Пара 3

Два близких кандидата строительного CV:

> Разработка системы обнаружения объектов на строительных объектах по изображениям
> с формированием визуальных протоколов

и

> Разработка системы оценки качества строительных швов с использованием компьютерного зрения
> и сегментацией дефектов

## Результат текущего lexical fallback

| Пара | Score |
|---|---:|
| 1 | 30.0 |
| 2 | 37.3 |
| 3 | 33.7 |

Если применять старый универсальный review threshold `45`, все три пары останутся без предупреждения.

При отдельном lexical threshold `25` все три пары попадают в ручную проверку.

## Вывод

**Допущение не подтвердилось.**

Lexical и embedding similarity имеют разные распределения score, поэтому им нельзя назначать
одинаковые пороги.

Решение:

- основной режим: `local-embedding`, review/high = `45/70`;
- fallback: `local-lexical`, review/high = `25/50`;
- фактический метод всегда сохраняется вместе со score.

Embeddings остаются основным способом ловить семантические перефразировки, lexical-only —
деградационный режим, а не равнозначная замена.

# Решения после spikes

В AI pipeline Lab 2 фиксируются следующие решения:

1. основной LLM structured output — **compact `titles[]`**;
2. длинные объяснения не запрашиваются, если они не нужны downstream;
3. Quality Gate выполняется локально;
4. semantic similarity не зависит от Mistral API;
5. основной duplicate-check — local multilingual embeddings;
6. lexical fallback имеет отдельные пороги;
7. сбой Mistral не маскируется demo-темами;
8. provenance модели сохраняется для каждого результата.

---

# Что ещё не доказано

Spikes не доказывают:

- что 8B лучше 3B на всём наборе преподавателей;
- что пороги `45/70` и `25/50` оптимальны на большой выборке;
- что latency compact output всегда укладывается в фиксированный SLA;
- что profile relevance score полностью коррелирует с оценкой преподавателя.

Это предмет следующих evals на golden dataset.

---

# Критерии для следующего эксперимента

На одном и том же наборе преподавателей сравнить 8B и 3B:

- ≥ 100 сгенерированных тем на модель;
- доля `passed`;
- доля профильных промахов;
- доля дублей;
- AI-repair на преподавателя;
- latency;
- input/output tokens;
- стоимость;
- доля тем, которые человек утвердил без редактирования.

Только после такого сравнения можно решать, допустимо ли автоматически использовать 3B как
production-degradation.
