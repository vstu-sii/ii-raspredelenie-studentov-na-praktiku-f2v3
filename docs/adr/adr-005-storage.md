# ADR-005: Supabase (managed Postgres) как хранилище прода

**Статус:** принято · **Дата:** 2026-09-29 · **Решают:** команда

## Контекст
MVP хранит: справочники (люди, темы, пары), статусы этапов, окна,
очередь уведомлений (ADR-004), кэш метаданных источников (ADR-003).
Команда не имеет своего сервера для БД; прод должен жить с первой
недели и не требовать администрирования. В вехе 2 появятся файлы
(PDF, архивы кода).

## Решение
Прод — Supabase как managed Postgres: схема и миграции — обычные
postgres-миграции, подключение через DATABASE_URL, драйвер стандартный.
Dev-окружение — локальный Postgres в compose.dev.yml (лаба 1): тот же
Postgres, те же миграции, dev не зависит от сети и от лимитов тарифа.
В вехе 2 файлы храним в Supabase Storage — не заводим отдельное
объектное хранилище.

## Альтернативы
- Самохост Postgres на VPS — отклонено: бэкапы, обновления, доступ
  извне — всё на команде, окупится только при своих серверах.
- MongoDB — отклонено: данные сильно реляционные (пары, приказы,
  статусы с внешними ключами), документная модель не даёт преимуществ.
- Railway/Neon (managed Postgres) — запасной вариант: тот же класс
  решения, переключение механическое (смена DATABASE_URL).

## Цена решения
Vendor lock-in умеренный: сама БД — стандартный Postgres, но auth
и Storage Supabase при использовании затягивают сильнее — поэтому
решаем заранее: auth делаем свой (MVP не нуждается в сложных ролях),
из Supabase берём только Postgres и позже Storage. Бесплатный тариф
засыпает при неактивности ~7 дней — для пилота с напоминаниями
активность постоянная, но на каникулах прод может уснуть: принимаем,
будим вручную. Единая точка отказа и общий пул нагрузки остаются:
тяжёлый отчёт может затормозить транзакции подачи пар — в MVP отчёты
ограничены дашбордом (UC-06), реплики не делаем до роста нагрузки.
