## Слайд 1. Из профиля преподавателя — в черновик темы

```mermaid
flowchart LR
    A["Профиль и запрос"] --> B["Фильтр команд в focus"]
    B --> C["Mistral генерирует темы"]
    C --> D["Проверка формата и повторов"]
    D --> E["Черновик в БД"]
```

На входе — научные направления, прошлые темы, количество новых тем и
пожелание пользователя. Модель видит числовой ID преподавателя.
Обязательные поля, ID, число и длина тем проверяются программно.
Лексический скрининг показывает возможные повторы. Подтверждает тему человек.
Повтор уже обработанного запроса в пределах TTL может получить ответ из кэша.

**Речь, 0:00–0:40.** «Преподавателю нужен стартовый список тем по своему
направлению. Мы берём профиль и прошлые темы, обрабатываем пожелание и
просим модель предложить кандидатов. Затем программа проверяет формат,
число тем и возможные повторы. Результат сохраняется как черновик.
Окончательное решение остаётся за руководителем».

## Слайд 2. Что изменилось за семестр

| Точка | Что проверено | Факт |
|---|---|---|
| ЛР3 | Облачная 8B, 4 кейса | 4/4 валидных пакета, p50 1,017 с |
| ЛР4 | Локальная 3B, 7 кейсов | v1 — 7/7, v2 и compact — по 5/7 |
| ЛР5 до точного ограничения количества | Локальная 3B, 20 кейсов | 9/20 пакетов, 43 вызова модели |
| ЛР5 после исправления схемы | Те же 20 входов | 20/20 пакетов, 20 вызовов, p50/p95 4,552/7,299 с |
| ЛР6, демо-кейсы через API и БД | Пять кейсов × три раунда на локальной 3B | 15/15 пакетов, p50/p95 9,112/31,783 с |

ЛР3 использовала другую модель и набор. Её задержка служит исторической
точкой. Сравнение до/после в ЛР5 выполнено на одном наборе и одной 3B.
В ЛР6 меняются выборка и граница замера, включая FastAPI и SQLite.
Данные этого демо-прогона приведены в [протоколе ЛР6](../demo-run.md).

**Речь, 0:40–1:20.** «В начале у нас был работающий вызов модели.
В четвёртой лабораторной более длинный промпт ухудшил долю валидных
ответов, поэтому мы оставили исходный. Расширенный набор выявил конкретную
проблему: модель возвращала несколько тем, когда просили одну.
Мы зафиксировали точное количество в JSON Schema. На тех же двадцати
запросах получили двадцать валидных пакетов вместо девяти и сократили
число вызовов с сорока трёх до двадцати».

## Слайд 3. Что показали проверки содержания

| Проверка ЛР5 | Результат |
|---|---:|
| Выполнение команды с контрольным маркером, без/с фильтром | 4/5 → 0/5 |
| Повторы с кэшем на пяти кейсах | 5/5 попаданий, 0 LLM-вызовов на повторах |
| Соответствие широкому профилю по рубрике ИИ-ассистента | 24/24 темы |
| Соблюдение совместимого пользовательского фокуса | 7/17 тем |
| Смысловые дубли по той же рубрике | 3/24, lexical-фильтр пометил 0/3 |

**Речь, 1:20–2:00.** «Валидный JSON ещё оставляет работу руководителю.
По оценке сохранённых тем модель часто держится научного направления,
но уходит от конкретного пожелания. Поэтому покажем и пример ограничения.
Явные команды в поле фокуса отфильтровываются, повторы можно обслужить
из кэша. Проверки содержания пока выполнены ИИ-ассистентом. Экспертная
приёмка и испытание всех атак остаются следующими шагами».

## Шпаргалка для вопросов

| Вопрос жюри | Ответ |
|---|---|
| Что дало наибольший прирост? | Точное количество тем в схеме, +11 валидных пакетов на 20 одинаковых входах |
| Почему выбрали v1? | На локальном A/B ЛР4 он вернул 7/7 пакетов, остальные варианты — 5/7 |
| Гарантируете уникальную тему? | Смысловую уникальность проверяет руководитель. В разметке ЛР5 обнаружены 3/24 смысловых дубля |

| А если модель упадёт? | Прогретый кэш, затем явный показ сохранённого ответа. Поведение холодного запроса и стрима проверено в ЛР6 |
