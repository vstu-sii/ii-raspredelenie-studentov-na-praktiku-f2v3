# Research — AI Engineer

## 1. Цель исследования

Цель AI-части проекта — определить подход к генерации тем ВКР на основе профиля преподавателя и его прошлых одобренных тем.

В рамках исследования сравнивались три варианта:

1. прямой вызов LLM со структурированным prompt;
2. RAG (Retrieval-Augmented Generation);
3. AI-агент.

Дополнительно сравнивались облачные модели и оценивалась не только стоимость API, но и нефинансовая цена решения: передача данных во внешнее облако, доступность сервиса и дополнительная инфраструктура.

---

## 2. Прямой structured prompt

Для генерации одной группы тем нам необходимо передать модели:

- научные направления преподавателя;
- его прошлые одобренные темы ВКР;
- направление подготовки;
- требования к формату новой темы;
- требуемое количество тем.

Такой объём информации для одного преподавателя небольшой и может быть передан непосредственно в контекст модели.

Современные LLM API позволяют дополнительно ограничивать формат ответа JSON-схемой. Например, Mistral поддерживает Structured Outputs и позволяет передавать пользовательскую JSON Schema.

Источники:

- https://docs.mistral.ai/studio/conversations/structured-output
- https://docs.mistral.ai/studio/conversations/structured-output/custom

### Вывод

Для первого MVP генератора тем отдельный retrieval-контур не является обязательным: профиль преподавателя и небольшой список прошлых тем можно передать непосредственно в prompt.

При этом одного ответа LLM недостаточно: после генерации требуется отдельная проверка соответствия профилю и смысловых дублей. Это подтвердилось в собственном эксперименте, описанном в `docs/experiments/lab1.md`.

---

## 3. RAG

Retrieval-Augmented Generation объединяет генеративную модель с внешней непараметрической памятью: перед генерацией система извлекает релевантные документы, а затем передаёт найденный контекст модели.

В исходной работе Lewis et al. RAG рассматривается как подход, объединяющий параметрическую память языковой модели и внешнюю непараметрическую память. Авторы показывают преимущества подхода на knowledge-intensive задачах и отмечают более конкретную и фактологичную генерацию по сравнению с parametric-only baseline.

Источник:

- https://arxiv.org/abs/2005.11401

Документация Mistral также описывает RAG как комбинацию retrieval релевантной информации и последующей генерации ответа с использованием полученного контекста.

Источник:

- https://docs.mistral.ai/resources/cookbooks/mistral-rag-basic_rag

### Вывод

RAG подходит нашему проекту для будущих сценариев, где необходимо работать с большим внешним корпусом:

- методические документы кафедры;
- научные публикации преподавателей;
- большой архив ВКР;
- проверка литературы;
- нормативные документы.

Для первой версии генерации тем по короткому профилю преподавателя RAG создаёт дополнительную инфраструктуру раньше, чем она становится необходимой.

Поэтому **в MVP RAG не используется как обязательная часть генератора тем**, но остаётся следующим этапом развития системы.

---

## 4. AI-агент

AI-агенты применяются в сценариях, где модель должна самостоятельно планировать последовательность действий, выбирать инструменты и выполнять несколько шагов.

Документация Mistral:

- https://docs.mistral.ai/studio/agents/introduction
- https://docs.mistral.ai/getting-started/quickstarts/developer/build-an-agent

В нашем текущем сценарии последовательность заранее известна:

1. получить профиль преподавателя;
2. получить его прошлые темы;
3. сформировать prompt;
4. запросить кандидаты у LLM;
5. проверить новые темы;
6. показать результат пользователю.

### Вывод

На этапе MVP автономный AI-агент не требуется, поскольку pipeline заранее определён программой.

Использование агента добавило бы дополнительное управление состоянием и инструментами, но не решило бы отдельную проблему контроля качества генерируемых тем.

---

## 5. Проверка похожести

Одна из выявленных проблем генерации — LLM способна переформулировать уже существующую тему другими словами.

Обычного сравнения строк для таких случаев недостаточно, поэтому дополнительно применяется семантическое сравнение через embeddings.

Mistral описывает embeddings как векторные представления текста, которые могут применяться для semantic search и поиска семантически близких текстов.

Источник:

- https://docs.mistral.ai/studio/knowledge-rag/embeddings

### Вывод

LLM используется как генератор кандидатов, но решение о качестве темы не должно приниматься только самой LLM.

После генерации тема должна отдельно проверяться как минимум на:

- смысловое сходство с прошлыми темами;
- сходство с другими темами текущего набора;
- соответствие научному профилю преподавателя.

## 6. Выбор модели

В качестве основной модели MVP выбрана:

**Ministral 3 8B (`ministral-8b-2512`).**

Модель поддерживает:

- Chat Completions;
- Structured Outputs;
- контекст до 256k токенов.

Официальная документация:

- https://docs.mistral.ai/models/ministral-3-8b-25-12

Официальная стоимость:

- $0.15 за 1 млн входных токенов;
- $0.15 за 1 млн выходных токенов.

Источник:

- https://docs.mistral.ai/inference/pricing

Выбор сделан не только по документации. Модель была подключена к прототипу и проверена на реальной генерации тем для преподавателей. Результаты описаны в `docs/experiments/lab1.md`.

### Почему выбрана именно эта модель

1. модель уже интегрирована в рабочий прототип;
2. поддерживает Structured Outputs;
3. успешно генерирует темы на русском языке;
4. стоимость одного сценария низкая;
5. реальный эксперимент показал, что модель способна сформировать полный набор тем, хотя часть кандидатов требует последующей автоматической и ручной проверки.

## 7. Сравнение стоимости моделей

Для сравнения используем один и тот же условный сценарий:

- 6000 входных токенов;
- 2000 выходных токенов.

### Ministral 3 8B

Цена:

- input: $0.15 / 1M токенов;
- output: $0.15 / 1M токенов.

Расчёт:

- 6000 × $0.15 / 1 000 000 = $0.0009;
- 2000 × $0.15 / 1 000 000 = $0.0003.

Итого:

**≈ $0.0012 за сценарий.**

Источник:

- https://docs.mistral.ai/inference/pricing

### GPT-4o

Цена:

- input: $2.50 / 1M токенов;
- output: $10 / 1M токенов.

Расчёт:

- 6000 × $2.50 / 1 000 000 = $0.015;
- 2000 × $10 / 1 000 000 = $0.020.

Итого:

**≈ $0.035 за сценарий (около $0.036 при округлении).**

Источник:

- https://developers.openai.com/api/docs/models/gpt-4o

### YandexGPT Pro 5.1

Цена синхронного режима:

- 0.8 ₽ / 1000 входных токенов;
- 0.8 ₽ / 1000 выходных токенов.

Расчёт:

- 6000 / 1000 × 0.8 ₽ = 4.8 ₽;
- 2000 / 1000 × 0.8 ₽ = 1.6 ₽.

Итого:

**≈ 6.4 ₽ за сценарий.**

Источники:

- https://aistudio.yandex.ru/ru/docs/ai-studio/pricing
- https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/models

## 8. Цена решения

Цена выбранного подхода состоит не только из стоимости API.

### 8.1. Денежная стоимость

Для выбранной модели Ministral 3 8B плановая стоимость одного сценария при бюджете 6000 входных и 2000 выходных токенов составляет около **$0.0012**.

Фактическая стоимость будет зависеть от реального количества переданных и сгенерированных токенов.

Источник:

- https://docs.mistral.ai/inference/pricing

### 8.2. Передача данных во внешнее облако

При использовании Mistral API переданный модели контекст обрабатывается инфраструктурой внешнего провайдера.

Это означает, что при передаче:

- профиля преподавателя;
- прошлых тем ВКР;
- фрагментов студенческих работ;

необходимо учитывать требования к конфиденциальности и не передавать лишние персональные данные.

Mistral указывает, что по умолчанию данные размещаются в Европейском союзе.

Источник:

- https://help.mistral.ai/en/articles/347629-where-do-you-store-my-data-or-my-organization-s-data

Для поддерживаемых stateless API Mistral также предоставляет режим Zero Data Retention на платных тарифах.

Источник:

- https://docs.mistral.ai/admin/monitor-comply/zero-data-retention

### 8.3. Доступность внешнего API

Облачное решение зависит от:

- доступности сети;
- доступности API провайдера;
- rate limits;
- политики провайдера.

Это особенно важно при сравнении с OpenAI. OpenAI публикует список стран, из которых поддерживается API. Россия в текущем опубликованном списке отсутствует.

Источник:

- https://help.openai.com/ru-ru/articles/5347006-which-countries-and-territories-are-supported-by-openai

Поэтому использование OpenAI API для системы, эксплуатируемой из России, создаёт дополнительный эксплуатационный риск.

### 8.4. Инфраструктурная стоимость

Текущий вариант требует:

- поддержки prompt;
- JSON Schema;
- логики проверки ответа;
- embeddings для проверки сходства;
- мониторинга ошибок и лимитов API.

Полноценный RAG дополнительно потребует:

- базы знаний;
- построения embeddings;
- vector storage;
- обновления индекса;
- настройки retrieval;
- оценки качества найденного контекста.

Именно поэтому для MVP выбран более простой pipeline без обязательного RAG.

## 9. Собственная проба

Подход был проверен на рабочем прототипе.

В эксперименте:

- выбраны 3 преподавателя;
- для каждого запрошено по 5 новых тем;
- всего получено 15 тем через Mistral AI;
- локальный банк тем не использовался.

Из 15 тем:

- 10 не получили индивидуального предупреждения Quality Gate;
- 5 потребовали дополнительной проверки из-за пограничной похожести либо слабого соответствия профилю.

Подробности:

- `docs/experiments/lab1.md`

### Вывод из эксперимента

Прямой LLM prompt позволяет получить рабочие кандидаты тем и поэтому достаточен для первой версии генератора.

При этом эксперимент показал, что **LLM нельзя использовать как единственный механизм контроля качества**.

Следовательно, выбран pipeline:

> **профиль преподавателя + прошлые темы → Ministral 3 8B → Structured Output → проверка профильной релевантности → semantic similarity → ручное подтверждение.**

---

## 10. Итоговое решение

Для MVP выбрана модель:

**Ministral 3 8B (`ministral-8b-2512`).**

Основной архитектурный подход:

**structured prompt + LLM + отдельный Quality Gate.**

RAG не исключается из проекта, но переносится на сценарии, где действительно требуется поиск по большому внешнему корпусу документов.

AI-агент на первом этапе не используется, поскольку последовательность действий известна заранее.

Решение основано одновременно на:

- внешних источниках;
- официальной документации моделей;
- расчёте стоимости;
- анализе эксплуатационных ограничений;
- собственном эксперименте на реальных профилях преподавателей.
